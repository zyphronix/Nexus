## Slide 02: Motivation — The Disconnected Surfaces Problem
* **Section:** 02 / 16 — Motivation
* **Title:** The Disconnected Surfaces Problem
* **Core Silos:**
  * **Surface 01 — Issue Tracker (Jira / Linear):** Structured task tracking with status boards, but lacks RAG and code awareness, remaining fully dependent on manual drag-and-drop updates (*No AI context • No code link*).
  * **Surface 02 — Chat Assistant (ChatGPT / Copilot):** Powerful conversational AI, but operates without persistent project memory, causing hallucinated task names and priorities on project-specific queries (*No backlog access • Hallucinates*).
  * **Surface 03 — Code Repository (GitHub):** Ground truth of what has shipped, but commit messages, diffs, and architecture docs never surface to the issue tracker or AI assistant (*Invisible to board • Invisible to AI*).
* **Key Pain Points:**
  * AI hallucinates task names and priorities.
  * Duplicate tasks are generated by agents.
  * 35–50% of tickets lag real progress by days.
  * Commit context never reaches the board.
* **Core Thesis:** *"A project manager becomes dramatically more useful when its chat, its task generator, and its board share one retrieval-augmented memory — and when the code repository writes back into the board automatically."*

## Slide 03: Research Gap and Aim
* **Section:** 03 / 16 — Research Gap & Aim
* **Title:** Research Gap and Aim
* **Competitive Gap Analysis (What Existing Tools Miss):**
  * **GitHub Copilot / Cursor:** Provides code autocomplete in the IDE, but has no visibility into backlog, roadmap, or task state.
  * **ChatGPT / Claude:** Provides conversational AI, but lacks persistent project memory and hallucinates task names.
  * **Jira / Linear:** Provides structured task tracking, but lacks RAG, code context, and relies on manual status updates.
  * **Notion AI:** Provides document Q&A, but is not structured for agile boards or commit-linked tasks.
* **Aim:** Design and implement a single platform where a **chat agent**, a **task-generation agent**, and the **Kanban board** share a unified retrieval-augmented context (spanning tasks, implementation plans, and GitHub source code) and where **git commits automatically reconcile with open tasks** via LLM-based fuzzy matching.
* **Novelty:** A single **Qdrant vector store** is reused across three semantic domains—tasks, plan sections, and code chunks—each with its own payload schema. This shared retrieval layer is exposed to both the **generative chat** and the **LangGraph architect agent**, ensuring neither produces work the codebase has already done.
* **Takeaway:** Fragmentation across surfaces is the root cause — unification through shared retrieval is the solution.

## Slide 05: Methodology — Core Concepts
* **Section:** 05 / 16 — Methodology
* **Title:** Core Concepts
* **01 — Retrieval-Augmented Generation (RAG):** The LLM receives a query-specific slice of an external knowledge base at inference time. Dense vector embeddings via **Gemini `gemini-embedding-001` (768 dimensions)** are stored in Qdrant and retrieved using cosine similarity with a score threshold of `0.3`.
* **02 — Three Parallel Semantic Indexes:** A single Qdrant cluster hosts three domain collections, all keyed on `project_id`:
  * `tasks` — title, description, status, priority, tags
  * `roadmap` — phase, section type, plan content
  * `code_chunks` — ~150-line overlapping file windows with path, SHA, language
* **03 — LangGraph Architect Agent:** A three-node directed graph (`Plan → Critique → Finalize`) handles structured task generation. The **Critique** node inspects the draft against RAG context and loops back to re-plan if quality falls below threshold. Uses typed state via `Annotation.Root` and validates output with **Zod**.
* **04 — LLM-Based Commit → Task Matcher:** Commit message + changed file list + open task list are sent to an LLM, which returns a strict JSON response `{taskIds: [...]}`. Validated IDs trigger bulk status updates without requiring `fixes #ID` syntax. Secured via OAuth 2.0 Authorization Code Flow with HMAC-SHA256 webhook verification.

## Slide 08: Implementation — RAG Pipeline
* **Section:** Implementation • Slide 08 / 16
* **Title:** RAG Pipeline
* **Subtitle:** Domain-specific indexing for tasks, roadmaps, and code chunks — enabling precise, project-scoped semantic retrieval via Gemini embeddings and Qdrant.
* **Indexing Path:** `Source Row / File` → `buildEmbeddingText()` → `Gemini embedContent (gemini-embedding-001, dim: 768, configurable)` → `Qdrant upsert (id • vector • payload)` into `tasks | roadmap | code_chunks`.
* **Retrieval Path:** `User Query` → `generateEmbedding()` → `Qdrant search (filter: { project_id }, topK, threshold: 0.3)` → `Top-K Payload Records merged into System Prompt`.
* **Key Architectural Design Details:**
  * **One Collection Per Domain:** Three separate Qdrant collections (`tasks`, `roadmap`, `code_chunks`) allow independent `topK` tuning and per-domain payload indexes.
  * **Deterministic Point IDs for Code:** `SHA-1` of `projectId:filepath:chunkIndex` reformatted as UUID enables idempotent reindexing of changed files without duplication.
  * **Smart-Skip Backfill:** Compares Qdrant point count to DB task count; skips redundant re-embedding unless `?force=true` is passed.
  * **Code Chunker Design:** 150-line windows with 20-line overlap, prefixed with `// File: <path> (lines N–M)` so the LLM retains file context even on standalone chunk retrieval.
  * **File Filter Rules:** Broad allowlist for code and docs; excludes generated/vendor paths, lockfiles, and binary-like files; caps file size at `200 KB` (`50 KB` for JSON/YAML).
* **Qdrant Payload Schema (Per Domain):**
  * `tasks`: `project_id`, `title`, `description`, `status`, `priority`, `tags`
  * `roadmap`: `project_id`, `phase`, `section_type`, `content`
  * `code_chunks`: `project_id`, `path`, `SHA`, `language`, `text`, `lines`

## Slide 09: Implementation — LangGraph Architect Agent
* **Section:** 09 / 16 — Implementation
* **Title:** LangGraph Architect Agent
* **Graph Execution Flow:**
  * `START` → **`[PLAN]`** (*"Draft tasks from RAG context"*) → **`[CRITIQUE]`** (*"Score + flag duplicates"*)
  * **Conditional Loop:** If `score < threshold`, loops back from `[CRITIQUE]` to `[PLAN]` (*"if score < threshold, re-plan"*).
  * **Completion:** Once threshold is met, transitions to **`[FINALIZE]`** (*"Emit tasks + audit log"*) → `END`.
* **Typed Agent State:** `requirement`, `techStack`, `existingTasks`, `plan`, `iteration`, `projectName`, `architecturalGuidelines`, `repoCodeContext`, `critique`, `finalTasks`.
* **Design Rationale:**
  * Explicit loop with termination on low critique score.
  * Typed state survives node boundaries.
  * Each node can use a different model or temperature.
  * Observable — every iteration is stored for traceability.
* **Anti-Duplication Hook:** `buildProjectContext()` injects existing tasks and repo code chunks into both the `Plan` and `Critique` prompts — so the agent reasons over the live board **and** actual files before generating anything new.

## Slide 10: Implementation — GitHub Integration
* **Section:** Implementation • 04 of 05
* **Title:** GitHub Integration
* **Subtitle:** Secure OAuth flow and webhook processing enable automated code indexing and natural-language commit matching to reconcile tasks without manual intervention.
* **Flow 1 — OAuth Connect:**
  1. **User Initiates:** `/api/auth/github/start`
  2. **GitHub OAuth:** State cookie • CSRF guard
  3. **Callback & Token:** `code → access_token`
  4. **Upsert Connection:** `github_connections` table
  5. **Select Repo:** Webhook registered → triggers **On-Connect Pipeline**:
     * `repos.get` (Default branch metadata) → `createWebhook` (HMAC secret registered) → `indexRepo()` (Tree walk → chunk → embed → upsert) → `Commit Backfill` (Last 30 days → LLM match → bulk close).
* **Flow 2 — Webhook Push:**
  1. **`POST /api/webhooks/github`:** `X-Hub-Signature-256`
  2. **HMAC Verify:** `timingSafeEqual • 401 on fail`
  3. **Lookup Connection:** `repo_full_name` lookup
  4. **`after()` Deferred:** Async reindex + match. For each commit: reindex added/modified/removed files, then send `msg + files + open tasks` to LLM → `{taskIds[]}` → validate → update.
  5. **Task Update:** `status → 'done'`
* **Key Design Decisions:**
  * **Security Note:** Current scope is `repo read:user` (broad); future hardening moves to repo-scoped auth + token encryption.
  * **Idempotent IDs:** `SHA-1` of `projectId:filepath:chunkIndex → UUID` ensures safe reindex on push.
  * **Tables Added:** `github_connections` (`project ↔ token + repo`) and `github_indexed_files` (`path + SHA + chunk count`).

## Slide 14: Conclusion
* **Section:** Conclusion • 14 / 16
* **Title:** Nexus unifies what fragmented tools keep apart.
* **Core Pillars:**
  * **Shared RAG Memory (One retrieval store, three domains):** Tasks, implementation plans, and code chunks indexed in a single Qdrant cluster — shared by chat, agent, and commit reconciliation alike.
  * **Agentic Planning (LangGraph critique loop):** The `Plan → Critique → Finalize` graph reasons against the same retrieval context, ensuring generated tasks are novel and grounded — not duplicates of existing backlog items.
  * **Closed Feedback Loop (Commits write back to the board):** LLM-based fuzzy matching reconciles push events with open tasks automatically, eliminating manual drag-and-drop status updates.
* **Key Contribution:** Retrieval-augmented memory is not merely a chat enhancement — it is a foundational substrate for agentic planning and source-code-aware project management. A single shared Qdrant store serving all three roles is the central architectural argument of this work.
* **Achieved Benchmarks:** `✓ Zero-hallucination chat` | `✓ < 30 s agent latency` | `✓ ≥ 80 % auto-close` | `✓ < 500 ms retrieval` | `✓ One-click GitHub connect`

## Slide 15: Limitations and Future Plan
* **Section:** 15 / 16 — Limitations & Future Plan
* **Title:** Limitations and Future Plan
* **Current Limitations:**
  * **Broad OAuth Scope:** GitHub access uses `repo read:user`, granting account-level repository visibility — over-permissioned for project needs.
  * **Plaintext Token Storage:** Access tokens stored unencrypted in `github_connections.access_token` — a security risk if database access is compromised.
  * **Single Branch Indexing:** Only the default branch is indexed; feature branch context is unavailable until merged.
  * **Pipeline Hardening Needed:** Webhook and matcher pipeline lacks idempotency, replay safety, and production-grade observability.
  * **Indexer Scale Limits:** Heavy resource usage on large repositories; no progress tracking or retry mechanism yet.
* **Future Plan:**
  * **01 — Highest Priority: Security-First Repository Access:** Move from broad OAuth scope to one-repository-per-project authorization using tighter, scoped permissions.
  * **02 — Token Encryption & Audit:** Encrypt tokens at rest via Vault or KMS; add credential rotation policies and strict access-audit trails.
  * **03 — Production Deployment:** Deploy to hosted, scalable infrastructure for consistent performance and high availability under real load.
  * **04 — Webhook Resilience:** Replay protection, idempotent processing, dead-letter queues, and monitoring dashboards for pipeline health.
  * **05 — Branch & PR Intelligence:** Branch-scoped indexing and PR-linked task insights — enabling early feedback before merge.
  * **06 — Evaluation Harness:** Labeled commit/task dataset for continuous precision-recall measurement of the LLM commit matcher.
